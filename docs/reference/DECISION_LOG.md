### ADR-001: Python вместо C++

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Оригинал написан на Excel/VBA. Нужен полный перепис с сохранением точности алгоритма. Выбор между Python и C++.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **Python** | Быстрая разработка, numpy для векторизации, огромная экосистема, PyQt6 для GUI, легко найти разработчиков | Медленнее C++ для чистого CPU, PyInstaller даёт большой exe |
| C++ | Максимальная производительность, маленький бинарник, контроль памяти | Долгая разработка, сложный GUI (Qt/C++), сложнее поддерживать, редкие специалисты |
| Rust | Безопасность памяти, производительность | Маленькая экосистема GUI, крутая кривая обучения, долгая разработка |
| Go | Простота, goroutines | Плохая поддержка GUI, numpy-аналоги слабее |

**Решение:** Python 3.12+

**Почему:**
1. Критический путь — алгоритм Type 1-5, который сложно отлаживать. Python позволяет быстро итерировать.
2. numpy даёт векторизацию, сравнимую по скорости с C++ для массовых операций.
3. PyQt6 — зрелый GUI-фреймворк с отличной документацией.
4. Проект расчитан на 1 разработчика — Python минимизирует time-to-market.
5. Производительность «достаточная»: 1000 образцов за 30 секунд — приемлемо для офлайн-инструмента.

**Trade-offs:**
- ✅ Быстрая разработка (3-4 недели вместо 3-4 месяцев)
- ✅ Легко тестировать и отлаживать
- ✅ Богатая экосистема (pandas, openpyxl, SQLAlchemy)
- ❌ Большой размер exe (~200-400 МБ с PyInstaller)
- ❌ Медленнее запуск (3 секунды vs мгновенно)
- ❌ GIL ограничивает threading (но не процессы)

**Последствия:**
- Используем PyInstaller для сборки exe
- Процессы вместо потоков для параллельности (обход GIL)
- Внимание к размеру exe — исключаем лишние библиотеки

### ADR-002: PyQt6 вместо PySide6

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Нужен кросс-платформенный GUI для Windows 10/11. Qt — очевидный выбор. Два официальных Python-биндинга: PyQt6 и PySide6.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **PyQt6** | Стабильный API, Riverbank Computing — 20+ лет опыта, хорошая документация, шире распространён | Коммерческая лицензия (GPL/LGPL), платная поддержка |
| PySide6 | Официальные биндинги от Qt Company, LGPL (более свободная лицензия), современный код | Менее стабильный API, меньше туториалов, некоторые баги в релизах |
| tkinter | Встроен в Python, нет зависимостей | Устаревший вид, плохая поддержка таблиц/графиков, сложно стилизовать |
| Dear PyGui | Лёгкий, быстрый, современный | Молодой проект, риск заброски, меньше функциональности |
| Kivy | Мобильный + десктоп | Перегружен для десктопа, непривычный API |
| wxPython | Нативный вид Windows | Медленная разработка, устаревшая документация |
| Electron | JS/HTML/CSS | Огромный размер, медленный, не нужен веб |

**Решение:** PyQt6

**Почему:**
1. PyQt6 — более зрелый и стабильный проект. PySide6 иногда имеет регрессии в новых релизах.
2. Больше русскоязычных и англоязычных туториалов.
3. Лучшая интеграция с matplotlib (QtAgg backend).
4. Для офлайн-приложения лицензия не критична (GPL совместим с распространением).
5. PyInstaller лучше поддерживает PyQt6 (меньше проблем с plugins).

**Trade-offs:**
- ✅ Стабильность и зрелость
- ✅ Больше ресурсов для обучения
- ✅ Лучшая интеграция с matplotlib/plotly
- ❌ Коммерческая лицензия Riverbank (не критично для внутреннего ПО)
- ❌ Немного тяжелее PySide6

**Последствия:**
- `pip install PyQt6`
- Используем `PyQt6.QtCore`, `PyQt6.QtWidgets`, `PyQt6.QtGui`
- Стилизация через QSS (Qt Style Sheets)
- Матplotlib backend: `Qt6Agg`

### ADR-003: SQLite вместо PostgreSQL

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Нужно хранить историю расчётов, версионировать алгоритм, поддерживать поиск и фильтрацию. База данных — локальная, без сетевого доступа.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **SQLite** | Встроенный, нулевая конфигурация, файл .db, переносимый, SQLAlchemy поддерживает из коробки | Не для многопользовательского доступа, ограниченная конкурентность |
| PostgreSQL | Мощный, надежный, масштабируемый | Нужен сервер, сложнее установка, избыточно для локального ПО |
| MySQL/MariaDB | Популярный | Нужен сервер, избыточно |
| JSON-файлы | Просто, человекочитаемо | Нет индексов, медленный поиск, риск повреждения |
| pickle | Быстро, Python-нативно | Не человекочитаемо, риск безопасности, версионирование сложно |
| LevelDB/RocksDB | Быстрый KV | Нет SQL, сложнее ORM |

**Решение:** SQLite + SQLAlchemy ORM + Alembic

**Почему:**
1. **Офлайн-режим:** Целевой ПК без интернета. SQLite не требует установки сервера.
2. **Переносимость:** .db файл можно скопировать на флешку и перенести.
3. **SQLAlchemy ORM:** Миграции, типизация, абстракция от SQL.
4. **Alembic:** Версионирование схемы БД при обновлениях приложения.
5. **Один пользователь:** Нет конкурентного доступа, SQLite достаточно.
6. **Размер:** 10 000 образцов — ~5-10 МБ, приемлемо.

**Trade-offs:**
- ✅ Нулевая конфигурация для пользователя
- ✅ Переносимость .db файла
- ✅ SQLAlchemy ORM — чистый Python-код
- ✅ Alembic миграции
- ❌ Нет многопользовательского доступа (не нужно)
- ❌ WAL-режим нужен для конкурентности (GUI + worker)
- ❌ Ограничение на размер (~281 ТБ — не достижимо для нашего случая)

**Последствия:**
- БД в `%APPDATA%/MINLITH/minlith.db`
- WAL journal mode для конкурентности
- Alembic в комплекте (сложности с PyInstaller — см. ADR-011)
- Резервное копирование: ручное копирование .db файла

### ADR-004: ProcessPool вместо ThreadPool

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Расчёт 1000+ образцов. Нужно ускорить без блокировки GUI. Выбор между потоками (threads) и процессами (processes).

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **ProcessPool** | Обходит GIL, истинный параллелизм на CPU, изоляция памяти (нет утечек), отмена — terminate процесса | Накладные расходы на fork/spawn, сложнее передача данных (pickle), сложнее отладка |
| ThreadPool | Легче, меньше накладных расходов, shared memory | GIL ограничивает CPU-bound задачи, риск race conditions, отмена сложнее |
| asyncio | Масштабируемость I/O | Не для CPU-bound, сложнее с numpy |
| Dask | Распределённые вычисления | Избыточно, сложность, зависимость от сети |
| Numba JIT | Ускорение без параллельности | Не решает проблему масштабирования, ограниченная совместимость |
| Cython | Компиляция в C | Сложность сборки, PyInstaller усложняется |

**Решение:** ProcessPoolExecutor (concurrent.futures) + QThread для GUI

**Почему:**
1. **GIL:** Расчёт Type 1-5 — чистый Python с условиями, numpy не помогает на этом этапе. GIL серьёзно ограничит ThreadPool.
2. **Изоляция:** Процесс можно убить при отмене без риска повредить основной процесс.
3. **Память:** Каждый процесс получает копию данных — нет shared state, меньше багов.
4. **Batch processing:** Группировка по типам позволяет эффективно использовать процессы (один тип — один процесс, меньше переключений).
5. **QThread:** GUI остаётся отзывчивым, ProcessPool работает внутри QThread.

**Trade-offs:**
- ✅ Истинный параллелизм (N ядер = N× ускорение)
- ✅ Простая отмена (terminate)
- ✅ Изоляция ошибок (процесс упал — остальные работают)
- ❌ Накладные расходы на spawn (~100-500 мс на процесс)
- ❌ Данные сериализуются через pickle (не критично для 1000 образцов)
- ❌ Сложнее отлаживать (логи через QueueHandler)
- ❌ Больше памяти (N процессов × данные)

**Последствия:**
- `multiprocessing.set_start_method('spawn')` на Windows
- Batch size = `max(10, N // cpu_count)`
- QueueHandler для логов из процессов
- Таймаут 120 секунд на процесс
- Temp SQLite для частичных результатов при отмене

### ADR-005: openpyxl вместо xlwings/xlrd

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Чтение и запись Excel-файлов (.xlsx, .xls). Оригинал в .xlsx с формулами и защитой.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **openpyxl** | Чистый Python, читает/пишет .xlsx, read_only режим, не требует Excel, активно поддерживается | Не читает .xls (устаревший формат), медленнее xlwings для больших файлов |
| xlwings | Интеграция с Excel, быстрый через COM | Требует установленный Excel, Windows-only, сложнее в exe |
| xlrd | Читает .xls | Не пишет, не поддерживает .xlsx (новые версии), заброшен |
| pandas | Удобный API, read_excel/write_excel | Тяжёлая зависимость, под капотом использует openpyxl/xlrd |
| pyxlsb | Читает .xlsb (бинарный Excel) | Только чтение, не наш формат |
| LibreOffice API | Бесплатный | Сложная интеграция, нестабильно |

**Решение:** openpyxl (основной) + xlrd (для .xls legacy)

**Почему:**
1. **Независимость от Excel:** Целевой ПК может не иметь Excel (или иметь LibreOffice). openpyxl работает без Excel.
2. **read_only:** Можно читать файл, открытый в Excel (не блокирует файл).
3. **Запись:** Создание новых файлов, добавление листов, форматирование.
4. **Активная поддержка:** Регулярные релизы, совместимость с новыми Excel.

**Trade-offs:**
- ✅ Не требует Excel
- ✅ read_only режим
- ✅ Активная поддержка
- ❌ Для .xls нужен xlrd (legacy)
- ❌ Медленнее COM-интеграции для огромных файлов
- ❌ Не поддерживает макросы VBA (не нужно — мы переписываем логику)

**Последствия:**
- `pip install openpyxl xlrd`
- Чтение: `openpyxl.load_workbook(path, read_only=True)`
- Запись: `Workbook()` или `load_workbook()` + `save()`
- Для .xls: `xlrd.open_workbook()`
- Работа с открытыми файлами: копирование во временный файл → запись → сохранение

### ADR-006: matplotlib + plotly вместо одного движка

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
6 базовых диаграмм + пользовательские. Нужен баланс между статичными (для отчётов) и интерактивными (для GUI).

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **matplotlib** | Стандарт де-факто, легко встраивать в PyQt6, экспорт PNG/SVG/PDF, треугольники (QAPF, A-CN-K) | Не интерактивный, устаревший API, медленный для больших данных |
| **plotly** | Интерактивный, красивый, веб-встраивание | Тяжёлый, сложнее встраивать в PyQt6, WebEngine зависимость |
| pyqtgraph | Быстрый, нативный для PyQt | Меньше типов диаграмм, плохие треугольники |
| bokeh | Интерактивный, веб | Требует сервер, сложно в десктопе |
| altair | Декларативный, красивый | Vega backend, тяжёлый, не для десктопа |
| VTK | 3D, мощный | Избыточно, огромный, сложно |
| QCustomPlot | Нативный Qt, быстрый | C++ библиотека, Python-обёртки слабые |

**Решение:** Два движка — matplotlib (основной) + plotly (интерактивный опционально)

**Почему:**
1. **matplotlib:** Надёжный для отчётов (PDF, Word). Встраивается в PyQt6 через FigureCanvasQTAgg. Треугольники (ternary) — через matplotlib.
2. **plotly:** Интерактивные диаграммы в GUI (hover, zoom, pan). Красивый pie chart и scatter.
3. **Плагиновая система:** Пользователь может выбрать движок для каждой диаграммы.
4. **Размер:** matplotlib входит в PyInstaller "бесплатно" (уже есть через numpy). plotly — опционально, можно исключить если критичен размер.

**Trade-offs:**
- ✅ Гибкость: статичные + интерактивные
- ✅ matplotlib — надёжный для отчётов
- ✅ plotly — красивый для GUI
- ❌ Две зависимости вместо одной
- ❌ plotly увеличивает размер exe
- ❌ Некоторые дублирования API

**Последствия:**
- `src/charts/engines/matplotlib_engine.py`
- `src/charts/engines/plotly_engine.py`
- Пользователь выбирает движок в настройках
- plotly можно отключить при сборке (флаг в build.py)

### ADR-007: reportlab + python-docx + jinja2 вместо LaTeX/Pandoc

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Генерация отчётов в PDF, Word, HTML. Конструктор отчётов drag-and-drop.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **reportlab** | Чистый Python, программное создание PDF, контроль верстки, встраивание matplotlib | Низкоуровневый, много кода для простых таблиц |
| **python-docx** | Чистый Python, нативный .docx, редактируемый результат | Только Word, не PDF |
| **jinja2 + HTML** | Шаблонизация, CSS, легко кастомизировать | Требует браузер/webkit для PDF, качество печати хуже |
| LaTeX | Идеальная типографика, научный стандарт | Требует TeX-дистрибутив, сложно на целевом ПК, кривая обучения |
| Pandoc | Универсальный конвертер | Требует установки, не чистый Python |
| WeasyPrint | HTML → PDF | Тяжёлые зависимости (GTK), сложно в Windows |
| fpdf2 | Лёгкий PDF | Меньше функций чем reportlab |
| xhtml2pdf | HTML → PDF | Устарел, баги |

**Решение:** reportlab (PDF) + python-docx (Word) + jinja2 (HTML)

**Почему:**
1. **reportlab:** Лучший контроль над PDF-версткой. Встраивание matplotlib-графиков. Не требует внешних программ.
2. **python-docx:** Пользователи геологов часто редактируют отчёты. .docx — редактируемый формат.
3. **jinja2 + HTML:** Простой шаблонизатор для HTML-отчётов. Просмотр в браузере, печать через браузер.
4. **Независимость:** Не требует LaTeX, Pandoc, WeasyPrint — всё чистый Python.

**Trade-offs:**
- ✅ Чистый Python, нет внешних зависимостей
- ✅ PDF с контролем верстки
- ✅ Редактируемый Word
- ✅ HTML для быстрого просмотра
- ❌ reportlab — многословный (низкоуровневый)
- ❌ Нет единого шаблона для всех форматов
- ❌ Размер exe увеличивается

**Последствия:**
- `src/reports/pdf_generator.py` — reportlab
- `src/reports/word_generator.py` — python-docx
- `src/reports/html_generator.py` — jinja2 + шаблоны
- Конструктор отчётов — единый UI, разные генераторы

### ADR-008: auto-py-to-exe вместо ручного PyInstaller

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Сборка .exe для Windows. PyInstaller — стандарт, но конфигурация сложная.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **auto-py-to-exe** | GUI-обёртка над PyInstaller, простая конфигурация, JSON-конфиг, визуальное управление | Ещё одна зависимость |
| PyInstaller (ручной) | Полный контроль, скрипт сборки | Сложная конфигурация hidden-imports, datas, binaries |
| cx_Freeze | Альтернатива PyInstaller | Меньше документации, реже используется |
| py2exe | Старый стандарт | Заброшен, не поддерживает Python 3.10+ |
| Nuitka | Компиляция в C++ | Долгая сборка, сложная отладка, не всё поддерживает |
| pynsist | Инсталлятор NSIS | Только инсталлятор, не portable exe |

**Решение:** auto-py-to-exe (GUI) + PyInstaller (CLI fallback)

**Почему:**
1. **auto-py-to-exe:** Упрощает конфигурацию PyInstaller через GUI. JSON-конфиг можно версионировать.
2. **PyInstaller:** Зрелый инструмент, поддерживает PyQt6, numpy, pandas.
3. **onedir:** Быстрее запускается чем onefile (не распаковывает при каждом запуске).
4. **--windowed:** Без консольного окна.

**Trade-offs:**
- ✅ Простая конфигурация
- ✅ JSON-конфиг под git
- ✅ Поддержка PyQt6, numpy, pandas
- ❌ Размер ~200-400 МБ (onedir)
- ❌ Антивирусы могут ложно срабатывать
- ❌ Медленный первый запуск (особенно onefile)

**Последствия:**
- `build.py` — скрипт автоматической сборки
- `auto-py-to-exe-config.json` — конфигурация
- `--onedir` режим
- `--windowed` флаг
- Исключение ненужных библиотек (tests, docs, .git)

### ADR-009: Frozen dataclasses вместо Pydantic/attrs

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Модели данных для входных/выходных структур. Нужна валидация, иммутабельность, сериализация.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **dataclasses (stdlib)** | Встроен в Python, легко, frozen=True, @dataclass | Нет встроенной валидации, меньше функций |
| **Pydantic** | Валидация, сериализация, JSON, производительность v2 | Ещё одна зависимость, тяжелее, избыточно для простых случаев |
| **attrs** | Мощнее dataclasses, валидация, converters | Ещё одна зависимость, менее популярно |
| **NamedTuple** | Иммутабельный, легкий, встроенный | Нет значений по умолчанию, устаревший подход |
| **TypedDict** | Для JSON-структур | Нет иммутабельности, нет методов |
| **классы __slots__** | Минимальная память | Много boilerplate |

**Решение:** dataclasses (stdlib) с `frozen=True`

**Почему:**
1. **Стандартная библиотека:** Нет дополнительных зависимостей. Меньше размер exe.
2. **frozen=True:** Иммутабельность — важна для безопасности данных (входные данные не должны меняться).
3. **Простота:** Минимальный синтаксис, читаемо.
4. **Валидация:** Отдельная функция `validate_sample()` — достаточно для нашего случая.
5. **Сериализация:** `asdict()` + json.dumps() — достаточно.

**Trade-offs:**
- ✅ Встроен в Python
- ✅ Простой и читаемый
- ✅ Меньше зависимостей
- ❌ Нет встроенной валидации (решаем отдельно)
- ❌ Нет JSON-схемы автоматически
- ❌ Меньше функций чем Pydantic

**Последствия:**
- `@dataclass(frozen=True)` для всех входных/выходных моделей
- `validate_sample()` в `core/validation.py`
- Сериализация через `dataclasses.asdict()`

### ADR-010: Логирование через stdlib logging вместо structlog/loguru

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Логирование операций, ошибок, debug trace. GUI-виджет для логов.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **logging (stdlib)** | Встроен, гибкий, QueueHandler для multiprocessing, RotatingFileHandler | Многословная конфигурация, устаревший API |
| **loguru** | Простой, современный, цвета, автоматическая ротация | Ещё одна зависимость, может конфликтовать с stdlib logging |
| **structlog** | Структурированные логи (JSON), контекст | Ещё одна зависимость, избыточно для десктопа |
| **watchdog** | Мониторинг файлов | Не логгер, избыточно |

**Решение:** stdlib logging + QueueHandler + GUILogHandler

**Почему:**
1. **Стандартная библиотека:** Нет зависимостей.
2. **QueueHandler:** Единый лог из всех процессов (multiprocessing).
3. **RotatingFileHandler:** Автоматическая ротация (10 МБ, 5 backups).
4. **GUILogHandler:** Кастомный Handler для вывода в QTextEdit.
5. **Уровни:** DEBUG (файл), INFO (файл+GUI), WARNING (файл+GUI), ERROR (файл+GUI+QMessageBox).

**Trade-offs:**
- ✅ Встроен в Python
- ✅ QueueHandler для multiprocessing
- ✅ Ротация файлов
- ❌ Многословная конфигурация (решаем через `utils/logger.py`)
- ❌ Менее красивый API чем loguru

**Последствия:**
- `src/utils/logger.py` — конфигурация
- `src/gui/widgets/log_widget.py` — QTextEdit + GUILogHandler
- Формат: `%(asctime)s - %(name)s - %(levelname)s - %(message)s`
- Файл: `%APPDATA%/MINLITH/logs/minlith.log`

### ADR-011: Alembic вместо ручных SQL-скриптов

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Миграции схемы БД при обновлениях приложения. Пользователь может иметь старую версию БД.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **Alembic** | Стандарт для SQLAlchemy, автоматическая генерация миграций, версионирование | Тяжеловат для встраивания в exe, требует шаблоны |
| Ручные SQL | Просто, контроль | Легко ошибиться, нет отката, сложно поддерживать |
| SQLAlchemy-Migrate | Устаревший | Заброшен |
| Django migrations | Мощный | Требует Django, избыточно |
| SQLite-only | `PRAGMA user_version` | Ручная работа, нет инструментов |

**Решение:** Alembic (с адаптацией для PyInstaller)

**Почему:**
1. **SQLAlchemy интеграция:** Работает с нашей ORM из коробки.
2. **Автогенерация:** `alembic revision --autogenerate` создаёт миграцию из изменений моделей.
3. **Версионирование:** Каждая миграция — отдельный файл, можно откатить.
4. **При запуске:** `alembic upgrade head` — автоматически применяет миграции.

**Trade-offs:**
- ✅ Автоматическая генерация миграций
- ✅ Версионирование
- ✅ Откат (downgrade)
- ❌ Сложнее встроить в PyInstaller (нужно включить шаблоны alembic)
- ❌ Дополнительный вес (~1-2 МБ)
- ❌ Нужна конфигурация `alembic.ini` в exe

**Последствия:**
- `src/database/migrations/` — папка с миграциями
- `alembic.ini` — конфигурация (включить в PyInstaller datas)
- При запуске: проверка версии БД → `upgrade head` если нужно
- Fallback: если Alembic сломан — создать таблицы заново (для новых установок)

### ADR-012: Настройки в JSON вместо Registry/INI

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Хранение пользовательских настроек (язык, тема, молярные массы, пути).

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **JSON** | Человекочитаемый, структурированный, Python-нативный, легко копировать | Нет комментариев, риск повреждения при ручном редактировании |
| Windows Registry | Стандарт Windows, интеграция с ОС | Windows-only, сложно бэкапить, не переносимый |
| INI | Простой, комментарии | Не иерархический, устаревший |
| TOML | Комментарии, типизация | Ещё одна зависимость (tomli для <3.11) |
| YAML | Читаемый, комментарии | Ещё одна зависимость, риск безопасности (yaml.load) |
| SQLite | Структурированный, запросы | Избыточно для простых настроек |
| QSettings | Нативный Qt, кросс-платформенный | Привязка к Qt, менее гибкий |

**Решение:** JSON (`settings.json`)

**Почему:**
1. **Переносимость:** Можно скопировать файл на другой ПК (офлайн-режим).
2. **Читаемость:** Пользователь может редактировать вручную (продвинутые).
3. **Python-нативный:** `json.load()` / `json.dump()` — нет зависимостей.
4. **Структура:** Иерархический (вложенные объекты для app, calculation, charts, export).

**Trade-offs:**
- ✅ Человекочитаемый
- ✅ Переносимый
- ✅ Встроен в Python
- ❌ Нет комментариев (используем README для документации)
- ❌ Риск повреждения при ручном редактировании
- ❌ Нет схемы валидации (проверяем кодом)

**Последствия:**
- `%APPDATA%/MINLITH/settings.json`
- `src/utils/config.py` — ConfigManager
- Валидация при загрузке: неизвестные ключи — игнорировать, отсутствующие — default
- Импорт/экспорт настроек через JSON

### ADR-013: Русский интерфейс (i18n-ready) вместо полного bilingual

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Язык интерфейса. Целевая аудитория — русскоязычные геологи.

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **Русский (основной)** | Понятно пользователям, быстрее разработка, нет overhead i18n | Сложнее добавить английский позже |
| Bilingual (ru/en) | Шире аудитория, профессиональный вид | Двойная работа, нужен переводчик, Qt Linguist сложность |
| Только английский | Стандарт для ПО | Непонятно целевой аудитории |

**Решение:** Русский интерфейс, но архитектура под i18n (Qt Linguist)

**Почему:**
1. **Целевая аудитория:** Геологи в РФ/СНГ. Русский — must have.
2. **Скорость:** MVP за 3-4 недели. Перевод удвоит время.
3. **Архитектура:** Все строки через `tr()` (PyQt6), .ts файлы — подготовлены для будущего перевода.
4. **Названия минералов:** Режимы "ru", "lat", "ru_lat" — уже предусмотрены.

**Trade-offs:**
- ✅ Быстрая разработка
- ✅ Понятно пользователям
- ✅ Архитектура готова для i18n
- ❌ Английский — только в будущем
- ❌ Нет перевода документации

**Последствия:**
- Все UI-строки через `self.tr("Текст")` или `QCoreApplication.translate()`
- `src/gui/translations/` — папка для .ts файлов
- `mineral_names` в настройках: "ru", "lat", "ru_lat"

### ADR-014: Производные группы вычисляемые, а не хранимые

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Производные группы (Pl, Fsp, Pel, Carsd, Ill+kn, Chl+Mm+Srp) — вычислять на лету или хранить в БД?

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **Вычисляемые (property)** | Нет дублирования, всегда консистентно, меньше памяти | Небольшой overhead при доступе |
| Хранимые в БД | Быстрый доступ, простые запросы | Дублирование, риск рассинхронизации |
| Хранимые + триггеры | Автоматическое обновление | Сложность, SQLite ограничен |

**Решение:** Вычисляемые через `@property` или методы

**Почему:**
1. **Консистентность:** Pl всегда = Ab + An, не может рассинхронизироваться.
2. **Меньше памяти:** Не храним 6 дополнительных полей в БД.
3. **Простота:** `minerals.pl = minerals.ab + minerals.an` — очевидно.
4. **БД:** Таблица `calculation_minerals` хранит только 24 базовых минерала.

**Trade-offs:**
- ✅ Нет дублирования
- ✅ Всегда консистентно
- ✅ Меньше памяти
- ❌ Небольшой CPU overhead (незначительно)
- ❌ SQL-запросы сложнее (нельзя `SELECT * FROM ... WHERE pl > 10`)

**Последствия:**
- `MineralComposition` — dataclass с `@property` для производных
- БД — только базовые минералы
- Фильтрация по производным — в Python (не в SQL)

### ADR-015: Округление только на выводе

**Статус:** Accepted  
**Дата:** 2026-07-17  

**Контекст:**
Excel оригинал использует ROUND на каждом шаге. Это создаёт накопление ошибок. Как поступить в новой версии?

**Рассмотренные варианты:**

| Вариант | За | Против |
|---------|-----|--------|
| **Максимальная точность, округление только на выводе** | Точнее, меньше накопления ошибок, современный подход | Расхождение с оригиналом > 0.01% |
| Точное воспроизведение Excel (ROUND на каждом шаге) | Совпадает с оригиналом | Накопление ошибок, сложнее код, менее точно |
| Гибрид: точность + коррекция | Баланс | Сложность, неочевидное поведение |

**Решение:** Максимальная точность (float64), округление только на выводе

**Почему:**
1. **Точность:** float64 даёт ~15 значащих цифр. Округление промежуточных — потеря точности.
2. **Современный подход:** Все научные вычисления — максимальная точность внутри, округление только для отображения.
3. **Сравнение с оригиналом:** Целевое расхождение < 0.01% — достижимо даже без промежуточных округлений.
4. **Проще код:** Не нужно отслеживать ROUND на каждом шаге.

**Trade-offs:**
- ✅ Максимальная точность
- ✅ Проще код
- ✅ Меньше накопления ошибок
- ❌ Небольшое расхождение с оригиналом (принимаем < 0.01%)
- ❌ Debug trace показывает "неокруглённые" значения

**Последствия:**
- Внутренние вычисления: `float64` (numpy) или `Decimal` (если критично)
- Округление: только в `ExcelWriter` и GUI-таблицах
- Настройка: `decimal_places` в settings.json (по умолчанию 2)
- Тесты: допуск ±0.01% от оригинала
