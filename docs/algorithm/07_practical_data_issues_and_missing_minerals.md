# Практические проблемы реальных данных и недостающие минералы

Эти вопросы не видны, пока считаешь на "чистых" учебных примерах, но обязательно вылезут на реальных XRF-анализах и погубят точность расчёта, если не заложить их в архитектуру заранее.

## 1. Конституционная вода (H₂O) и LOI

Многие минералы из набора — **гидратированные**: каолинит, иллит, хлорит, гиббсит, гипс. Их формулы содержат H₂O, которого нет в списке "главных оксидов" вашего README (SiO₂...SO). Есть два источника этой воды в реальном анализе:

- **LOI (Loss on Ignition, потери при прокаливании)** — суммарная потеря массы при прокаливании образца, включает и конституционную воду, и CO₂ из карбонатов, и окисление Fe²⁺→Fe³⁺ (для последнего иногда нужна обратная поправка).
- **H₂O⁻ и H₂O⁺** раздельно, если лаборатория даёт их отдельно (сорбционная вода при 105°C и структурная вода при прокаливании) — H₂O⁺ и есть то, что нужно балансировать с гидратными минералами.

**Что нужно сделать в реализации:**
1. Добавить в модель состава (`OxideComposition`) поле для LOI и/или H₂O⁺/H₂O⁻/CO₂, если их ещё нет.
2. Перед расчётом минералов проверять: **достаточно ли H₂O⁺ (или LOI за вычетом CO₂ из карбонатов), чтобы "покрыть" конституционную воду всех гидратных минералов, которые получились по балансу оксидов**. Если H₂O⁺ в анализе меньше, чем требуется по стехиометрии посчитанных гидратных минералов — это **сигнал ошибки** (либо порода менее глинистая, чем показал формальный Al-баланс, либо LOI не был измерен/введён, и нужно явно предупредить пользователя).
3. Если LOI вообще отсутствует в исходных данных — явно помечать выходной отчёт как "минеральный состав рассчитан без учёта LOI; фактические вес.% гидратных минералов могут быть занижены/завышены, нормировка выполнена без them" — это честная и полезная информация для геолога, использующего программу.

## 2. Разделение Fe₂O₃/FeO (проблема тотального железа)

Многие современные XRF-анализы дают **только суммарное железо** (обычно как Fe₂O₃(общ.) или FeO(общ.)), не разделяя Fe²⁺/Fe³⁺ — это требует отдельного титриметрического определения (метод Уилсона/бихромата), которое часто не делается вместе с XRF.

Если у вас на входе только суммарное железо, а модель расчёта ожидает раздельные FeO и Fe₂O₃ — нужно либо:
- запрашивать оба значения отдельно (жёсткое требование к входным данным, самый честный вариант);
- либо **эмпирически расщеплять** суммарное железо на FeO/Fe₂O₃ по known correlations для конкретного типа осадочных пород (степень окисленности обычно оценивается по литологическому типу — красноцветные породы почти всё Fe³⁺, серые/зелёные глины — заметная доля Fe²⁺). Общепринятого универсального коэффициента для осадочных пород (в отличие от магматических, где есть методики вроде Le Maitre, 1976) я подтвердить не могу — это либо параметр, задаваемый пользователем явно (например, "предположительная степень окисленности" как настройка расчёта), либо ещё один параметр для калибровки по вашим эталонным данным.

**Рекомендация для архитектуры**: сделайте разделение Fe₂O₃/FeO **явным входным параметром/режимом**, а не скрытой автоматической эвристикой — пользователь-геолог должен видеть и по возможности контролировать это допущение, потому что оно сильно влияет на итоговое распределение (магнетит/гематит/силикаты/карбонаты).

## 3. Замыкание анализа (closure) и нормировка на 100%

Реальные анализы редко дают сумму оксидов ровно 100% (в примере из файла `06` — 92.7%, без LOI). Есть два разных момента, которые часто путают:

- **Нормировка входа** — привести сумму вес.% оксидов к 100% *до* расчёта минералов (то есть чуть увеличить каждое значение пропорционально). Это меняет абсолютные цифры, но не меняет относительные пропорции между оксидами — расчёт минералов даст пропорционально те же относительные результаты.
- **Нормировка выхода** — после расчёта минералов их сумма (в силу гидратной воды, округлений, недостающего LOI) не будет ровно 100% сама по себе; насколько сильно она отличается от 100% — **диагностический показатель качества расчёта**, и его не стоит скрывать простой пере-нормировкой без предупреждения. Разумная практика: показывать пользователю и нормированный вес.% (для удобства сравнения), и абсолютную сумму до нормировки (для контроля качества).

**Рекомендация**: реализовать обе нормировки как явные, разделённые шаги с логированием (сколько было исходное расхождение, сколько — после расчёта), а не скрывать в одной "магической" функции — это прямо соответствует вашему уже описанному Debug trace collector.

## 4. Недостающие минералы для Fe-Mg составов (см. проблему №2 из файла 06)

Список из файла `02` не покрывает случай, когда после исчерпания Al₂O₃ остаются значительные FeO/MgO. Разумные дополнения (по важности для типичных осадочных пород):

### Глауконит (Glt) — важно для морских зеленоватых песчаников/алевролитов
Твёрдый раствор переменного состава, упрощённая практическая формула (K,Na)(Fe³⁺,Al,Mg)₂(Si,Al)₄O₁₀(OH)₂ — в оксид-молекулярной записи для программной реализации разумно использовать сильно упрощённый вариант вроде `(K₂O)₀.₅(Fe₂O₃)(SiO₂)₄(H₂O)` (числа ориентировочные, глауконит — один из самых "плавающих" по составу минералов в природе, и для него в любом случае нужна отдельная калибровка, если порода предположительно глауконитовая — это обычно определяется заранее по геологическому контексту/цвету/местоположению в разрезе, не только по формальному оксидному балансу).

### Биотит (Bt) — если есть одновременно K₂O, Fe/Mg и Al₂O�3
`K(Mg,Fe)₃(AlSi₃O₁₀)(OH)₂` → оксид-молекулярная запись: `(K₂O)(MgO,FeO)₆(Al₂O₃)(SiO₂)₆(H₂O)₂` (на удвоенную формулу). Стоит считать **до** каолинита в порядке стадии 2, если K₂O ещё не исчерпан ортоклазом и в остатке есть заметный FeO/MgO — то есть это ещё один аргумент за пересмотр жёсткого порядка "сначала весь K в ортоклаз" (см. проблему №1 в файле 06).

### Простой "аварийный" Fe-Mg силикат без Al и K (запасной вариант)
Если ни глауконит, ни биотит не подходят по геологическому контексту, а Fe/Mg всё равно остаются — минимальный вариант: минерал типа серпентина/тальк-подобный `(MgO,FeO)₃(SiO₂)₂(H₂O)₂` как чисто "техническая заглушка", чтобы баланс сходился, с explicit-пометкой в выводе, что этот минерал — не строгая петрографическая интерпретация, а способ закрыть баланс (аналог того, как в CIPW есть "магнетит vs гематит" как техническое разделение, а не геологическая точность).

## 5. Порядок реализации этих поправок (рекомендация)

1. Сначала — базовая версия без глауконита/биотита/LOI-проверки (просто по файлам 00-04), чтобы получить работающий скелет и посчитать на учебных примерах.
2. Добавить нормировку и явную диагностику LOI/closure (раздел 1 и 3 этого файла) — это чисто инженерная работа, не требует новых геологических знаний.
3. Добавить Fe₂O₃/FeO как явный конфигурируемый параметр расчёта (раздел 2).
4. В последнюю очередь — расширить список минералов (глауконит/биотит/аварийный силикат) и пересмотреть порядок K₂O между ортоклазом и иллитом через параметризованный коэффициент (это самая "геологическая" и самая требующая калибровки часть, разумно делать её последней, когда уже видно на реальных прогонах, для каких именно составов не хватает баланса).

## 6. Заметка по производительности (раз в README упомянут ProcessPoolExecutor)

Сама последовательность вычислений (стадии 1→2→3) — чисто арифметическая, без итеративных решателей, поэтому для одного образца она уже очень быстрая (микросекунды). Параллелизация имеет смысл не внутри одного расчёта, а **по образцам** — то есть именно так, как у вас уже сделано (ProcessPoolExecutor на уровне пробы). Если нужно ещё большее ускорение для очень больших выборок (тысячи проб), стоит рассмотреть векторизацию через numpy/pandas — переписать весь конвейер стадий как операции над столбцами DataFrame (каждая проба — строка, каждый оксид — столбец), тогда вместо `for sample in samples: calculate(sample)` считать все пробы одной проходкой матричных операций. Это даст на порядки больший выигрыш, чем параллелизация процессов, для по-настоящему больших объёмов (десятки-сотни тысяч образцов), но потребует переписать ветвления (min/условия по типу породы) как маскированные операции над массивами (`np.where`, булевы маски), а не как построчный Python-код — если объём данных у вас не в этом масштабе, текущий ProcessPoolExecutor-подход вполне достаточен и проще в поддержке.
